# KNOWN_ISSUES

## 1. ドキュメントの目的

現在コードから確認できる既知の問題を管理する。業務仕様自体は本書で変更しない。

## 2. 分類と重大度

- Critical：情報漏えい、権限回避、データ破壊等につながる可能性
- High：主要機能が誤動作する、または運用への影響が大きい
- Medium：一部機能の不整合、保守性低下、エラー処理不足
- Low：未使用コード、命名、軽微な品質問題
- Unknown：影響を確定できないため追加確認が必要

## 3. 既知の機能不整合

### ISSUE-001：お知らせ画面のimport不整合

- 重大度：High
- 分類：機能不整合
- 確認できた事実：`TeacherView`は`NoticeManager`名で`NotificationManager.jsx`をimportしている。実際の`NoticeManager.jsx`は未使用。
- 業務への影響：お知らせ画面で対応キュー用UIが表示され、お知らせ専用機能が利用されない。
- 根拠：`src/TeacherView.jsx:8,188-190`、`src/components/NoticeManager.jsx`
- 再現・確認方法：講師系ロールで初期表示の「お知らせ」を確認する。
- 未確認事項：本番で意図的に通知キューを代用しているか。
- 提案：未決定の提案として、業務仕様確認後に正しいコンポーネントへ接続する。

### ISSUE-002：生徒進捗取得effectの重複

- 重大度：Medium
- 分類：重複処理
- 確認できた事実：同じ`activeMenu`依存で`fetchCompletedUnits()`を呼ぶeffectが2つある。
- 業務への影響：画面切替時に同一API取得が重複し、負荷や表示競合が増える。
- 根拠：`src/StudentView.jsx:77-81,135-139`、action `getStudentSchoolProgress` / `getStudentKoToreProgress`
- 再現・確認方法：検証環境のNetworkで進捗画面切替時の要求数を確認する。
- 未確認事項：GAS側の負荷・課金への実影響。
- 提案：未決定の提案として、業務仕様確認後に単一effectへ統合する。

### ISSUE-003：未使用・類似コンポーネント

- 重大度：Low
- 分類：保守性
- 確認できた事実：`SchoolProgress.jsx`、`SukimaKun.jsx`、`NoticeManager.jsx`は未参照。`PastReviewModal`はimportのみ。`PastReviewView`と類似する。
- 業務への影響：実装箇所の誤認、誤修正の可能性。
- 根拠：import参照調査、`src/StudentView.jsx:9`
- 再現・確認方法：各コンポーネント名をリポジトリ内検索する。
- 未確認事項：将来利用予定か旧実装か。
- 提案：未決定の提案として、履歴と予定を確認後に整理する。

### ISSUE-004：学校進捗コンポーネント名の入れ替わり

- 重大度：Low
- 分類：命名
- 確認できた事実：講師側は`SchoolProgressManager.jsx`を`SchoolProgressTracker`名で、生徒側は`SchoolProgressTracker.jsx`を`SchoolProgressManager`名でimportしている。
- 業務への影響：保守時に対象を取り違える可能性。
- 根拠：`src/TeacherView.jsx:10`、`src/StudentView.jsx:6`
- 再現・確認方法：import元とローカル名を比較する。
- 未確認事項：命名に意図があるか。
- 提案：未決定の提案として、役割に沿った名称へ統一する。

### ISSUE-005：レスポンス成功判定とエラー表示の不足

- 重大度：Medium
- 分類：例外処理
- 確認できた事実：複数処理で`result !== success`時の表示がない。`deleteNotification`はレスポンス成功判定を行わない。
- 業務への影響：保存・削除・取得失敗を利用者が成功と誤認する可能性。
- 根拠：`src/TeacherView.jsx:101-112`、各TrackerのAxios処理
- 再現・確認方法：検証用APIで失敗応答を返し、画面反応を確認する。
- 未確認事項：GASが常にHTTPエラーを返す設計か。
- 提案：未決定の提案として、action別の失敗表示を統一する。

### ISSUE-006：空のcatchによる通知取得失敗の黙殺

- 重大度：Medium
- 分類：例外処理
- 確認できた事実：生徒通知ポーリングの`catch`が空である。
- 業務への影響：対応完了状態を取得できなくても利用者に通知されない。
- 根拠：`src/StudentView.jsx:224-236`、action `getNotifications`
- 再現・確認方法：検証環境でAPI取得を失敗させる。
- 未確認事項：一時障害時に静かに継続する意図か。
- 提案：未決定の提案として、連続失敗時だけ状態表示する方式を検討する。

### ISSUE-007：APIタイムアウト・再試行なし

- 重大度：Medium
- 分類：通信信頼性
- 確認できた事実：Axiosのtimeout、AbortController、自動再試行を設定していない。
- 業務への影響：通信が完了しない場合にローディング状態が長時間継続する可能性。
- 根拠：リポジトリ内Axios呼出全般。
- 再現・確認方法：検証環境で応答を保留する。
- 未確認事項：インフラ側タイムアウト値。
- 提案：未決定の提案として、許容時間と再試行対象actionを業務確認する。

### ISSUE-008：CSVの単純split解析

- 重大度：Medium
- 分類：データ解析
- 確認できた事実：CSVを改行とカンマの`split`で解析する。依存する`papaparse`は使用されない。
- 業務への影響：引用符付きカンマ、改行等を含む教材名・単元名を正しく解析できない可能性。
- 根拠：`src/StudentView.jsx:124-132`、`src/App.jsx:35-42`、`package.json`
- 再現・確認方法：引用符付きカンマを含む検証CSVで確認する。
- 未確認事項：現在のマスターに該当値が存在するか。
- 提案：未決定の提案として、CSV仕様確定後にパーサーを統一する。

### ISSUE-009：ESLintが失敗する

- 重大度：Medium
- 分類：品質管理
- 確認できた事実：`npm run lint`は46エラー・5警告で終了する。未使用変数、不規則空白、Hooks依存等を含む。
- 業務への影響：静的品質チェックを合格条件として利用できない。
- 根拠：2026-08-05の読み取り専用ESLint結果。
- 再現・確認方法：依存追加なしで`npm run lint`を実行する。
- 未確認事項：CIでlintを必須としているか。
- 提案：未決定の提案として、機能変更と分離して警告を分類・解消する。

### ISSUE-010：巨大コンポーネントとAPI処理重複

- 重大度：Medium
- 分類：保守性
- 確認できた事実：`StudentView.jsx`等の一部画面では、状態・通信・UIが同一componentに残っている。通信処理も機能ごとに実装されている。
- 業務への影響：仕様変更時の影響範囲が広く、エラー処理の不一致が生じやすい。
- 根拠：各ファイル、`src`内Axios呼出。
- 再現・確認方法：行数、責務、重複するPOST処理を確認する。
- 未確認事項：今後の保守体制。
- 提案：未決定の提案として、仕様確定後に通信・変換・表示責務を段階的に分離する。

### ISSUE-011：READMEが初期テンプレートのまま

- 重大度：Low
- 分類：ドキュメント
- 確認できた事実：`README.md`はViteテンプレートの説明で、業務アプリの起動・環境・運用情報がない。
- 業務への影響：新規担当者が安全な開発・検証方法を把握できない。
- 根拠：`README.md`
- 再現・確認方法：全文確認。
- 未確認事項：別の運用手順書の有無。
- 提案：未決定の提案として、正式仕様書へのリンクと非機密の開発手順を整備する。
